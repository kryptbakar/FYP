# Evaluation protocol

How VYREX's investigation layer will be evaluated, **decided before any results exist** so
the design cannot be shaped by what happens to look good.

This document is deliberately written in advance. Choosing metrics after seeing outcomes is
how honest projects end up with dishonest conclusions.

---

## 1. What is being evaluated

**Question.** Does an evidence-grounded, citation-bound investigation graph help an analyst
triage more accurately or faster than the tools they already have?

**Three systems, compared on the same findings:**

| # | System | What the analyst sees |
|---|---|---|
| A | Score + SHAP only | Today's console: composite score, factor waterfall, no narrative |
| B | One-shot LLM (`/agent/triage`) | The deprecated single-call agent: a verdict and a reason, no evidence |
| C | Investigation graph | Cited verdict, per-node trace, inspectable evidence |

B matters. Without it, any advantage of C could simply be "an LLM helps" rather than
"**this** design helps", and the entire contribution of the graph would be unevidenced.

---

## 2. The labelling problem, stated honestly

Accuracy needs ground truth. VYREX has **none**: `analyst_feedback` is empty, and the ML
layer's existing metrics are circular (labels generated by the formula under test — see
[METHODOLOGY.md §4.1](METHODOLOGY.md)). Repeating that mistake here would invalidate the
whole evaluation.

Two things are therefore forbidden:

- **Scoring a model against another model's output.** LLM-as-judge with no human anchor is
  circularity wearing a different hat.
- **Using the system's own verdicts as labels.** The agent cannot be its own ground truth.

### The constraint that shapes everything: this is a solo project

Standard practice would be 100–150 cases, two blind reviewers each, adjudicated
disagreements. **One person cannot be two blind reviewers.** Pretending otherwise would be
the single easiest thing for an examiner to dismantle.

The substitute, which is defensible if executed exactly as written:

**1. Temporal blinding.** Every case is labelled **before** the system is run on it.
The label is committed (git, timestamped) and never revised. This is real blinding — at
labelling time the system's output does not exist, so it cannot influence the label.

**2. A rubric frozen before labelling starts.** Written and committed first, so labels
cannot drift toward whatever the system happens to do. Minimum content:
- what distinguishes ESCALATE from MONITOR from DISMISS
- when INSUFFICIENT_EVIDENCE is the *correct* answer rather than a cop-out
- how to weigh KEV / EPSS / corroboration / asset criticality against each other

**3. Advisor adjudication on a ~20% subsample.** The only genuine second-rater signal
available. Produces a real Cohen's κ. **Secure this commitment early** — it cannot be
retrofitted, and without it there is no inter-rater statistic at all.

**4. Target: 60–80 cases**, not 150. Stratified across severity, domain, source tool, KEV,
IOC presence, corroboration level, and *deliberate* missing-evidence cases.

> An honest n=60 with a documented blinding protocol is worth more than a dubious n=150.
> State the limitation in the thesis rather than waiting to be asked about it.

**5. Corpus expansion is on the critical path.** As of 2026-08-28 the database holds ~54
findings. Reaching 60–80 *stratified* cases needs more: additional scan fixtures, more
simulated assets, and Atomic Red Team on the lab VM. This is calendar-bound work — start it
first, because no amount of effort later compresses it.

## 3. Metrics

### 3.1 Decision quality (needs labels)

| Metric | Why |
|---|---|
| Macro-F1 on disposition | Treats all four classes equally; accuracy would be dominated by the majority class |
| Confusion matrix | *Which* errors matter — a missed ESCALATE is not a wrongly-dismissed MONITOR |
| Weighted agreement on severity | Ordinal: HIGH-vs-CRITICAL is a smaller error than LOW-vs-CRITICAL |
| Abstention quality | Of the INSUFFICIENT_EVIDENCE answers, how many were cases a human also could not call? Abstaining correctly is a **success** |

### 3.2 Grounding quality (no labels needed — measurable today)

| Metric | Why |
|---|---|
| Citation validity | Do cited ids resolve to collected evidence? |
| **Uncited-verdict rate** | Verdicts with zero citations. Currently **6/6** for llama3.2:3b — nothing it says is attributable |
| Claim support (human-reviewed) | Does the cited evidence actually support the claim, or merely exist? |
| Retrieval recall@k | Did the specialists surface the evidence a human considered decisive? |

Grounding is separable from accuracy and measurable **now**. A model that is right for
unsupported reasons is not usable in a SOC, and this is where that shows up.

### 3.3 Operational (no labels needed)

p50/p95 latency · completion vs failure vs partial rate · repeated-run variance at
temperature 0 · peak CPU and RSS · **analyst time-to-triage** (the metric a SOC actually
buys).

## 4. Study design

**Counterbalanced ordering.** No participant sees the same case in the same order with and
without assistance; otherwise the second pass is faster because the case is familiar, not
because the tool helped.

**Ablations** — this is what shows which parts of the design earn their place, and is the
difference between "I built five nodes" and "I showed which of the five matter":

| Ablation | Question |
|---|---|
| − historical context | Does prior-triage context change verdicts? |
| − threat intel | How much is MISP carrying? |
| − fusion (corroboration) | Is multi-tool consensus doing real work, or is it decoration? |
| − asset context | Does criticality/compliance shift anything? |
| single prompt vs graph | Is the structure worth it, or would one big prompt do? |

That last row is the one an examiner will ask about. Answer it with data.

**Implemented:** `make model-benchmark ... --drop {asset|attack|intel|fusion|historical}`.
Each evidence record carries the citation prefix of the specialist that produced it, so an
ablation is a filter rather than graph surgery, and the remaining set is byte-identical to
a real run without that branch. Pinned by 8 tests, including one asserting that an unknown
ablation name raises rather than silently producing a full-evidence run — which would look
exactly like "this branch changes nothing".

**And it cannot discriminate yet, for a reason that is not a bug.** Dropping asset context
across 3 cases: 3/3 `INSUFFICIENT_EVIDENCE`, evidence 7 → 6 records. The baseline is
*already* 100% abstention, so removing evidence cannot move a verdict that was never
committed. **Ablations require a model that decides.** The mechanism is built, tested and
ready; the measurement is blocked by the same ceiling as everything else in §3.4, and will
produce signal the moment a model returns something other than abstention.

What it *does* already show: ablation changes the evidence count as expected and the run
still completes and stays schema-valid, so a missing branch degrades rather than breaks —
which is the Phase 2 invariant, independently confirmed.

## 4b. Preliminary three-system comparison — label-free, and already awkward

`eval/compare_systems.py` compares A, B and C on measures needing **no labels**.
Run 2026-08-29, `llama3.2:3b`:

| System | Cases | ESCALATE | MONITOR | DISMISS | INSUFFICIENT | Cited |
|---|---|---|---|---|---|---|
| **A** composite score only | 63 | 0 | 61 | 2 | 0 | 0 |
| **B** one-shot LLM | 15 | 6 | 5 | 4 | 0 | 0 |
| **C** investigation graph | 10 | 0 | 0 | 0 | **10** | 0 |

**Read this before drawing the obvious conclusion.** On the only axis measurable today —
*does the system discriminate at all* — **B looks better than C**. B spreads across three
classes; C abstains on everything. The sophisticated system is the one that says nothing.

That is a real finding and it stays in the write-up. Three things must be said alongside
it, none of which are excuses:

1. **This measures discrimination, not correctness.** B's six escalations may be wrong; no
   label exists to say. A system that guesses confidently outscores one that abstains on
   *every* label-free metric, which is precisely why §2 forbids stopping here.
2. **C's abstention is caused by the constraints that make it trustworthy.** B has no
   schema, no citation requirement and no evidence store, so it cannot fail to produce a
   verdict — there is nothing for it to fail *against*. C must cite collected evidence, and
   a non-abstaining verdict citing nothing is rejected by contract. The abstention is the
   constraint working, on a model that cannot satisfy it
   ([AGENT-ORCHESTRATION.md](AGENT-ORCHESTRATION.md) §7). **The honest framing is a trade,
   not a win:** B offers unverifiable answers, C offers verifiable silence.
3. **A barely discriminates either**, for a duller reason: no finding in this corpus scores
   ≥ 60, so the ESCALATE band is empty and 61 of 63 land in MONITOR. That independently
   confirms the plan's warning that an automatic trigger at 60 would fire on nothing.

**What would change the conclusion.** If, once labelled, B's confident verdicts prove
frequently wrong while C's abstentions land on genuinely undecidable cases, C is the better
system and the abstention-quality metric will show it. If B is largely right, the graph's
contribution is grounding and auditability rather than accuracy — a narrower claim, and the
one to make. Either way the comparison decides it, not the architecture's elegance.

## 5. Threats to validity — stated, not buried

| Threat | Mitigation | Residual |
|---|---|---|
| Single labeller | Temporal blinding, frozen rubric, advisor κ on 20% | Real. State it. |
| Small corpus (~60) | Stratification; report confidence intervals | Wide intervals; no fine-grained claims |
| Lab data, not production | Atomic Red Team for out-of-distribution behaviour | Generalisation unproven |
| Hardware ceiling | 5.8 GiB for Docker, CPU-only; 3–4B models only | Results may not hold for larger models — say so |
| Fixture-backed intel | MISP is 6 IOCs; OpenCTI is 7 SQL predicates | Do not claim live intel integration |
| Labeller built the system | Unavoidable solo | The strongest reason the rubric must be frozen first |
| **Corroboration cases are engineered** | Marked `lab:synthetic`; see below | **Do not present `n_tools` as independent agreement** |

### The corroboration caveat — read this before quoting any fusion number

On 2026-08-29 the corpus was expanded to meet §10's stratification targets. Reaching the
"≥6 corroborated" target was done by **adding MISP IOCs for IP addresses the Sigma rule had
already flagged**. That is engineering the overlap: the tools agree because the fixtures
were chosen to make them agree.

This is legitimate as *evaluation input* — the labeller and the agent see the same evidence,
so the comparison between them stays fair, and the fusion mechanism genuinely needs cases to
exercise. It is **not** evidence that independent tools converge in the wild.

Concretely, this is what may and may not be said:

- ✅ "Fusion clusters findings from three tools on a shared observable, and here is a case."
- ✅ "The clustering key was wrong until 2026-08-28; here is the regression test."
- ❌ "Three tools independently agreed, therefore the finding is more likely true."
- ❌ Any base rate — *"X% of findings are corroborated"* — computed on this corpus.

The new IOCs are tagged `lab:synthetic` in `services/intel-enricher/fixtures/ioc.json` so
they can be excluded from any analysis where their provenance matters.

The original `185.220.101.45:4444` cluster is the one exception worth naming: it was
corroborated **before** the corpus was expanded, and its three-tool agreement emerged from
fixing the clustering key rather than from adding matching intel. It is the honest example
to demo.

---

## 6. Exit criteria

The evaluation is complete when:

- results, confidence intervals, limitations and **raw anonymised scoring sheets** are all
  recorded;
- no metric is computed against labels derived from the thing being measured;
- lab data is clearly separated from fixtures and seeded demo data;
- every quoted number names the model, the graph version and the hardware it came from.

The freeze is only meaningful if it is checkable, so it is: the rubric was committed with an
empty `eval/labels/`, and every label carries `rubric_version` plus a timestamp. Anyone can
verify from git history that the rubric predates the labels, and that the labels predate the
investigation runs. That audit trail is the entire substitute for a second blind reviewer —
which is why §12 of the rubric makes labels append-only.

**Nothing here licenses an accuracy claim yet.** What *can* be reported today is grounding
and operational behaviour — and the current finding there is stark: llama3.2:3b produces
schema-valid output, abstains on every corroborated case, and cites nothing at all. That is
a reportable result about the model, not about the pipeline.
